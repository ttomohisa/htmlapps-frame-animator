# Frame Animator — APP_SPEC.md

## 1. Product identity

- **Name:** Frame Animator
- **Japanese display name:** Frame Animator
- **Repository:** `ttomohisa/htmlapps-frame-animator`
- **Slug:** `frame-animator`
- **Current milestone:** v1.0.1 (stable)
- **Purpose:** Import multiple local still images, arrange and time them, preview the motion, and export Animated GIF or Animated WebP without uploading source images.
- **Primary users:** People creating simple animations from photos, screenshots, burst shots, Before/After images, and numbered image sequences.
- **Release artifacts:** Follow the current `htmlapps-template` build contract: readable standalone HTML, gzip self-extracting HTML, and the repository-root readable copy generated by the build.

## 2. Problem and outcome

Creating an animation from several still images often requires uploading images to an online converter. Frame Animator keeps that workflow local: images are selected, decoded, normalized, previewed, encoded, and saved in the browser.

The intended completed flow is:

1. Add JPEG / PNG / still WebP images.
2. Reorder frames.
3. Set a global or per-frame duration.
4. Choose canvas sizing and Fit / Fill.
5. Preview Forward / Reverse / Ping-pong playback.
6. Generate Animated WebP or GIF.
7. Review the generated Blob and save it.

## 3. Positioning

Frame Animator is distinct from:

- **Video to GIF / WebP:** converts a selected time range from a video source.
- **Pixel Animation Studio:** creates and edits small pixel-art frames.

Frame Animator handles ordinary still photos and screenshots as animation frames. It is not a drawing app or a general-purpose image editor.

## 4. Input contract

### Supported by v1.0.0

- JPEG / JPG
- PNG
- still WebP

Input methods:

- multiple file selection
- Drag & Drop
- add-more flow
- clipboard image paste by v0.7.0

Unsupported in v1.0.0:

- video
- GIF input
- Animated WebP input
- APNG
- HEIC / HEIF
- AVIF
- SVG
- PSD
- PDF

Animated WebP must not be silently treated as a still image when detectable.

## 5. Limits

Initial v1.0.0 guards:

- maximum 200 imported frames
- maximum 50 MiB per source file
- maximum 500 MiB total source file bytes
- maximum 50 megapixels per source image
- maximum output canvas 4096 × 4096

These are application safety guards, not claims about browser-wide hard limits.

## 6. v0.1.0 functional requirements

v0.1.0 is the image-import foundation.

It must:

- use the current Browser Kitty template structure
- keep `connect-src 'none'`
- support Japanese and English in one HTML
- load JPEG, PNG, and still WebP
- support multi-select and Drag & Drop
- allow more images to be added to the current session
- show a thumbnail, filename, dimensions, megapixels, and source size for each accepted image
- reject unsupported or invalid images without failing the entire batch
- report partial failures separately from accepted images
- detect and reject Animated WebP when detectable from the RIFF/VP8X/ANIM structure
- enforce frame-count, per-file, total-byte, and pixel-count guards
- avoid holding full decoded RGBA data for every imported image
- generate lightweight thumbnails and revoke obsolete Blob URLs
- not persist user images to localStorage or IndexedDB
- provide a destructive confirmation before clearing every imported image
- expose a fully scrollable help dialog on smartphones
- remain usable at narrow smartphone widths

v0.1.0 does **not** claim GIF / WebP export is implemented yet.

## 6.1 v0.2.0 functional requirements

v0.2.0 adds the frame sequence editor on top of the v0.1.0 import foundation.

It must:

- reorder frames by pointer/touch drag from a dedicated drag handle
- provide earlier/later buttons so reordering never depends on drag alone
- duplicate a frame without duplicating the original source-file bytes
- delete a single frame immediately and offer Undo
- provide global Undo / Redo controls and Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, and Ctrl/Cmd+Y where they do not interfere with text/form editing
- sort frames by filename ascending or descending using natural numeric ordering
- make sorting reversible
- keep sequence history bounded and release thumbnail Blob URLs that are no longer reachable
- disable sequence editing while a new import is actively decoding
- keep the current total-source-size display based on unique active source images, so duplicating a frame does not pretend that the original file bytes were copied
- keep the v0.1.0 import limits, partial-failure behavior, local-only processing, and no-image-persistence policy

The language switch uses compact labels: `EN` while Japanese is active and `JA` while English is active.

## 6.2 v0.3.0 functional requirements

v0.3.0 adds frame timing and a live motion preview.

It must:

- assign a default duration of 500 ms to newly imported frames
- preserve a frame's duration when the frame is duplicated
- allow each frame to use an independent duration from 20 to 10,000 ms
- normalize frame durations to 10 ms steps when the value is committed
- provide 100 / 200 / 500 / 1000 ms apply-to-all presets
- provide a custom apply-to-all duration input
- show the total animation duration from the current frame sequence
- include timing changes in the existing bounded Undo / Redo history
- preview frames using their actual durations rather than converting the sequence to a fixed FPS
- provide Play / Pause, Restart, Previous, and Next controls
- show the current frame number, elapsed playback position, total duration, and progress
- start playback only after an explicit user action; do not autoplay imported images
- continue playback after a duration edit when playback was already active
- pause and reset current-frame timing when sequence order or history changes invalidate the active schedule
- make clear that this is a motion/timing preview, not a final encoded-quality preview

The live preview may loop continuously in v0.3.0. User-configurable playback order and loop count remain planned for v0.7.0.

## 6.3 v0.4.0 functional requirements

v0.4.0 adds a shared output-canvas normalization model.

It must:

- resolve one output canvas for mixed source dimensions and aspect ratios
- use the first active frame aspect ratio for Auto, 480, 720, 1080, and Original-equivalent modes
- default to Auto: first-frame aspect ratio with a long edge up to 720 px and no upscaling when the first frame is smaller
- provide 480 / 720 / 1080 long-edge presets
- provide an Original-equivalent mode, capped to the 4096 px output limit
- provide Custom width and height from 16 to 4096 px
- provide Fit, which keeps the complete source image visible and centers unused canvas space
- provide Fill, which fills the complete canvas and center-crops overflow
- provide transparent, white, black, and custom-color backgrounds
- show transparency with a checkerboard behind the preview canvas
- recalculate preset canvas geometry when the first frame changes through reorder/history
- use source image dimensions for placement geometry even when the preview uses a lightweight thumbnail
- decode preview image data on demand and close ImageBitmap resources after drawing
- avoid retaining full-resolution RGBA buffers for the entire frame sequence
- centralize canvas-size and placement calculations so the same geometry can be reused by GIF / WebP encoders
- preview timing from v0.3.0 on the normalized output canvas

The v0.4.0 preview may use a lower-resolution local thumbnail as its pixel source for responsiveness. It must still use the same output dimensions, source aspect-ratio geometry, Fit / Fill calculations, and background settings as the future encoder path.

## 6.4 v0.5.0 functional requirements

v0.5.0 adds local Animated GIF generation.

It must:

- generate a standards-compatible GIF89a animation from the current frame sequence
- use the v0.4.0 output canvas, Fit / Fill placement, background, and full-resolution source files
- decode and normalize one source frame at a time instead of retaining full-resolution RGBA for the entire sequence
- transfer each normalized RGBA buffer to a Blob Worker so color quantization, dithering, and LZW compression do not block the main UI thread
- provide 64 / 128 / 256 color output with 256 as the default
- use a weighted histogram / median-cut style palette reduction suitable for photographic and gradient content
- provide Floyd–Steinberg dithering, enabled by default
- support transparent GIF output when the canvas background is transparent
- convert alpha to GIF's 1-bit transparency using a threshold and use disposal behavior that clears transparent frames correctly
- support infinite looping and play-once output
- preserve per-frame duration from 20 to 10,000 ms, rounded to GIF centiseconds
- expose encoding progress by frame and allow cancellation
- terminate the Worker and reject pending work when conversion is cancelled
- preview the actual generated GIF Blob before saving
- show generated dimensions, frame count, total duration, and file size
- provide an editable output filename with a predictable `.gif` extension and filename sanitization
- invalidate a generated result whenever an output-affecting frame, timing, canvas, color-count, dithering, or loop setting changes
- keep old/stale generated files unavailable for Save
- remain fully local with no runtime dependency, network request, analytics, or telemetry

The GIF encoder uses a per-frame palette. This improves color allocation across different photographic frames but GIF remains limited to at most 256 colors per frame and 1-bit transparency.

The built-in GIF encoder is first-party application code and does not add a third-party runtime package.

## 6.5 v0.6.0 functional requirements

v0.6.0 adds Animated WebP export and two workflow refinements requested during implementation.

It must:

- keep the initial image drop area large before any image is loaded
- switch the image drop area to a compact horizontal layout after one or more frames exist
- preserve both file-picker import and Drag & Drop after the drop area becomes compact
- use the supplied `frame-animator-basic-shapes.svg` artwork unchanged as `assets/favicon.svg`
- use that same SVG for both the browser favicon and the in-app brand icon through the template icon embedding path
- export Animated WebP locally from the existing full-resolution normalized frame pipeline
- use pinned `@jsquash/webp@1.5.0` assets embedded in the standalone HTML
- pin the npm tarball by SHA-256 and npm integrity in `dependencies.lock.json`
- run static WebP encoding in a Blob module Worker and pass the embedded libwebp WASM bytes directly so the encoder performs no runtime fetch
- preserve each frame duration in milliseconds in WebP `ANMF` chunks
- build the WebP animation container locally with `VP8X`, `ANIM`, and full-canvas `ANMF` chunks
- use no-blend full-canvas frames so each frame replaces the previous frame deterministically
- support Quality 1–100 with default 80
- support Lossless mode
- support Effort / libwebp method 0–6 with default 4
- support infinite looping and play-once output
- preserve alpha when the normalized output canvas is transparent
- show per-frame preparation / encoding progress and allow cancellation
- terminate Worker work and revoke Worker/module Blob URLs on completion, cancellation, failure, or page exit
- preview the actual generated Animated WebP before saving
- show generated dimensions, frame count, duration, and file size
- use a separate editable `.webp` filename
- invalidate stale WebP output whenever shared frame/timing/canvas settings or WebP-specific settings change
- preserve GIF output from v0.5.0
- keep `connect-src 'none'`; add only the CSP capability needed to instantiate the embedded WASM
- add no server-side processing or runtime CDN dependency

The WebP implementation intentionally does not reuse the video-oriented FFmpeg WASM profile because that profile is built around video demux/decode and fixed-FPS video conversion. Frame Animator instead encodes each normalized still frame directly with libwebp and constructs the animation container locally, preserving the app's variable frame durations.

## 6.6 v0.7.0 functional requirements

v0.7.0 unifies playback behavior across preview, GIF, and WebP and adds workflow polish.

It must:

- provide one shared playback-order setting used by preview, GIF export, and WebP export
- support Forward, Reverse, and Ping-pong order
- build Ping-pong as `1 → 2 → 3 → 4 → 3 → 2`, excluding duplicate endpoint frames
- keep the editable frame list unchanged when playback order changes; playback order is a derived sequence
- show the derived frame count and one-pass duration
- support shared loop behavior: infinite, once, or a custom play count from 2 to 100
- stop preview automatically after the configured finite play count
- restart a completed finite preview from the beginning when Play is pressed again
- map shared loop behavior correctly to each format:
  - GIF: no Netscape loop extension for once, 0 for infinite, and `playCount - 1` repeats for finite custom counts
  - Animated WebP: 0 for infinite and the requested finite play count otherwise
- use the derived playback sequence for exported frame order, frame count, and per-pass duration
- include finite loop multiplication when showing generated-result duration
- invalidate both GIF and WebP results when playback order or loop settings change
- accept JPEG / PNG / still WebP images pasted from the clipboard when focus is not inside an editable form control
- generate deterministic local filenames for pasted clipboard images before importing them through the same validation path as selected files
- warn before unusually heavy export workloads while still allowing the user to continue
- base the heavy-job warning on resolved canvas pixels and derived playback-frame count, not on source-file bytes alone
- retain the separate visible `.gif` and `.webp` filename suffixes
- sanitize an entered filename base and strip a mistakenly entered `.gif` or `.webp` extension before appending the format-correct extension
- preserve the v0.6.0 compact add-image drop zone, supplied icon/favicon, pinned WebP dependency, local-only runtime, and EN / JA switch

The heavy-job warning is advisory. It must not silently reduce canvas size, color count, quality, frame count, or other user settings.

## 12. Encoding architecture

Keep encoding behind an `AnimationEncoder`-style abstraction so frame/UI logic does not depend on one backend.

GIF implementation must be validated for photographic content; the compact encoder in Pixel Animation Studio must not be assumed suitable for full-size photos without quality and performance tests.

Animated WebP should use a dedicated local encoder such as a minimal libwebp/WebPAnimEncoder WASM build or an equally focused image-sequence profile. Do not reuse the existing video decode/demux profile unchanged.

Heavy encoding must run off the main thread when practical and support cancellation.

## 13. Memory strategy

Do not decode and retain every full-resolution source image as RGBA.

Preferred flow:

1. Keep original `File` references.
2. Create small thumbnails for the frame list.
3. Decode source frames on demand.
4. Normalize one frame to the output canvas.
5. Feed the encoder.
6. Release temporary bitmap/canvas resources.
7. Continue to the next frame.

Revoke Blob URLs when removed, cleared, replaced, or on page teardown.

## 22. v1.0.1 timing and safe-import refinement

- The existing timing toolbar adds 0.5× slower and 2× faster actions. Each action doubles or halves every current frame duration, rounds to 10 ms, and clamps to 20–10,000 ms. It preserves the sequence and relative timing wherever rounding/limits permit.
- Each effective speed action is one Undo/Redo history entry, invalidates both encoded results, and resumes active live playback using the new schedule. Empty, busy, and no-change actions do not add history.
- Undo restores exact durations. The opposite speed button is not guaranteed to reverse a rounded or clamped change.
- APNG is rejected before image decoding by scanning PNG chunk headers up to IDAT, including large preceding metadata. Malformed/truncated chunks and excessive metadata chunk counts fail safely.
- Animated WebP detection uses the actual RIFF/WEBP header, even for a misleading filename/MIME type. Rejected additions leave existing frames, timing, and generated results intact; valid members of the same batch still import.
- The language switch retains EN/JA and exposes its destination in a tooltip and accessible name written in the active UI language. Help includes speed semantics and animated-input limitations.
- Validation must inspect saved GIF and WebP frame durations, edited filenames, source-image loss on reload, retained language preference, and readable/root/self-extract offline opening.

- The self-extract loader preserves only the source CSP's `wasm-unsafe-eval` capability because both loader and restored-document policies apply. It must not grant general `unsafe-eval`; network access remains blocked. Regression checks cover matching permission presence/absence and reject broader or mismatched policies.

- Completed imports render in the ready state so GIF/WebP format tabs are immediately usable. The persistent partial-failure report shows the actual accepted count from that batch.
